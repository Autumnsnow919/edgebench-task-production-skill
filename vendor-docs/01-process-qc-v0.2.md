# Bench 过程小样融合版质量检查指引（出题后、跑轨迹前；仅检查与报告）

## 1. 目标与边界

本指引主要用于**出题后、模型轨迹运行前**检查过程小样目录或 ZIP，并生成一份独立的 Markdown 质检报告。检查对象可以包含任务题面、输入、Verifier、参考解、运行环境、控制运行、办公工件及说明材料；若包内已有模型轨迹，也检查其来源和口径。检查覆盖材料完整性、内容清洁度、任务定义质量、实际运行及报告一致性；**第三方材料的许可证、授权与再分发核查不在本版范围内**。不能把过程小样说成已完成最终交付验收。

**本流程不编写、改写或输出 `README.md`。** 包中已有 README 时，将它作为交付文件、解题者可见材料或任务线索进行检查；客户明确要求 README 而最终包缺失时，记录为交付缺陷。检查不因缺少非必需 README 而扣分，也不把 README 文案质量单列为 Task 质量分项。除非用户另行明确要求修复，本流程只读检查，不修改待检包。

以客户当前书面要求为最高适用口径。先区分客户硬要求、项目约定和本指引的检查建议；未规定的目录、命名、运行方式或成功阈值不能自行升级为硬标准。若客户要求与本指引的默认建议冲突，报告采用客户要求并说明适用依据。

本指引不评价多题组合的领域、语言、题型、GPU 比例、成功率分布或总体代表性，也不由小样推断模型或 Benchmark 的总体能力。没有可运行任务、Verifier、参考解或轨迹时，相应专项检查说明不适用，不伪造运行结论。

**阶段适用性。** 跑轨迹前应尽量完成公开题面、输入、环境、Verifier、参考解及必要 Oracle/NOP/Static 的实质检查；模型 trial、强弱模型对比、成功轨迹 Step/wall time、轨迹修订和训练价值只有存在相应证据或本次明确声称时才检查。尚未计划产生的轨迹标为 `N/A（本阶段未运行）`，已要求但未能完成的必要控制运行标为 `BLOCKED`；两者不能混用。报告中的“成功轨迹”“模型成功率”等字段可写“本阶段未运行，不适用”，不填零或虚构值。后续跑轨迹、修订题目或进入正式交付时，应依据新增证据重新核对受影响项；本次过程检查不自动替代后续验收。

## 2. 开始检查前确认

记录客户要求的版本或日期、最终包路径、交付形式、必需材料、允许的包外文档、文件格式、命名、权限、禁用内容、运行要求及报告字段。对会改变结论但尚未提供的信息，标记 `BLOCKED`，继续完成其他可确定的检查。

核验脚本、临时解压目录、日志和质检报告均放在待检包之外。先从**本次送检的过程包**重新枚举全部目录和文件，建立逐文件覆盖清单；嵌套容器内的文件另计，并记录父子关系。每个文件至少记录相对路径、用途、材料类别、格式、检查方法、读取状态、结论及证据或阻塞原因。文件总数与本次送检包重新枚举的数量一致；不能因为文件加密、损坏或工具不支持就将其从清单删除。

任务材料包括题面、测试、参考实现、fixtures、数据、环境与运行配置；独立交付说明、轨迹说明和质检报告属于说明材料。先给文件定类，再应用对应规则。类别不明时标为 `BLOCKED`，不能靠改名获得豁免。

**任务文件语言。** 对当前项目的任务/instruction/prompt 及其他实际喂给模型的输入，检查运行原件是否为英文；中文译件只能作面向中文客户的独立说明，不能替代模型实际看到的原件。用创建记录、版本历史或试跑输入核对“先有英文原件、后有译件”和运行输入的一致性；只有当前文件时只能确认当前语言，不能臆断创作顺序，缺少会影响复现结论的来源证据应标 `BLOCKED`。面向美国客户的交付说明及英文交付包的目录、文件名按已确认的项目/客户约定检查英文和 ASCII；不得将语言或路径建议擅自变成所有客户的通用门槛。

## 3. 检查执行顺序

1. **交付与逐文件审阅。** 对照本阶段客户清单检查缺失、错放、重复、历史版本和无用途文件。用相应解析器检查 JSON、TOML、CSV 等结构化文件；检查文本编码、引用、空文件、损坏、截断、扩展名与真实格式、权限和归档元数据。默认文本建议 UTF-8 无 BOM、LF，客户有明确格式时从其要求。shell 脚本应有 shebang；交付要求保留 POSIX mode 时核对脚本 `0755`、普通文件 `0644` 和目录 owner 可写，Windows 解压目录不能证明 mode 时读归档或版本库元数据。对源码和纯文本阅读全文；对 PDF、Office、媒体、数据库及嵌套归档检查正文、隐藏内容、元数据和可提取结构。关键词扫描只用于定位候选，不能替代全量审阅。嵌套归档在包外防路径穿越地展开。
2. **泄露与隔离。** 检查正文、注释、路径、文档属性、批注、修订、嵌入对象和实际读写权限中的凭据、私有答案、seed、canary、内部人名、其他客户名及本机路径。项目已有 canary 时核对同批一致性及放置位置；没有约定不强加。发现真实凭据时报告精确位置并建议走既有安全流程，未经授权不代为吊销或轮换。任务材料不得出现模型名或工具名；独立说明材料可准确披露轨迹来源，但仍须满足其他清洁要求。本步骤不检查第三方许可证或再分发权。
3. **先读公开题面，再审私有实现。** 独立写出目标、输入、输出、成功条件、必要约束与一种合法解。影响答案的单位、时点、边界、异常处理和规则优先级应能由公开材料确定。随后审参考解和 Verifier，建立“公开要求 → 验收检查”和“验收检查 → 公开依据”的双向对应。隐藏样本、数值阈值和探针可以保留，但评估目标与必要统计口径应公开；不得因隐藏阈值本身扣分，也不得暗加无必要的过程或表示限制。
4. **验证真值与判别能力。** 用输入的独立推导、可信来源或小型算例核查参考结果；参考解和 Verifier 共用同一公式时，不能互相充当独立证明。逐条检查 criterion 是否只对应一个可独立判断、有业务意义的事实或交付要求，明确证据对象与失败边界，不因换种说法重复扣分。二元 Reward 的必需项应限于缺失后足以使核心结论不可信、产物不可用或关键业务风险失控的要求；轻微排版或非必要术语不能单独使整题归零。复杂判定附近应能看出业务理由、通过/失败/未解决边界及字段、解析或聚合的实现理由，特别核对负向项反转、解析失败、单位转换与异常值处理；缺少注释本身不单独扣质量分，只有造成可定位的不可解释性或评分风险时归入相应 Q 项。检查 Verifier 是否验真实产物或行为，能否拒绝空执行、缺失或损坏产物及核心错误变体，并接受题意允许的等价解。运行异常、测试跳过、真实失败和 Reward 聚合分别核对。同一根因不重复扣分。
5. **执行必要控制运行。** 客户要求可运行、可复现，或用 Oracle、NOP、Static 声称质量时，优先复用同题版、同环境、同 Verifier 的可信原始证据；不足处实际运行。Oracle 从正式初态在规定预算内执行参考解，经正式交接和正式 Verifier 评分。NOP 从独立干净初态执行真正的空操作，再跑正式 Verifier；不能继承 Oracle 的可写状态。镜像缓存可复用，但复用工作区、构建产物或可写卷不得描述为独立干净构建/初态。核对运行时输入、临时材料、证据、最终产物和框架收集入口的位置及交接，不依赖作者机器的绝对路径、默认 Documents、autosave 或临时导出。评分器私有文件在 Agent 阶段不可见。办公工件应从正式输出路径用相应应用重新打开，检查公式、图表实际引用范围、媒体/交互、可编辑性及跨产物同一指标的一致性；不能只看文件存在或格式解析。Static、Oracle、NOP 和模型轨迹各自记录，互不替代。静态脚本存在、外层命令退出成功或局部单测均不等于正式运行通过。
6. **核对已有轨迹及修订。** 本阶段尚无模型 trial 时，本步的 trial 明细不适用；已有 trial 则逐条关联实际题版、Verifier 版、环境与资源配置、模型与推理配置、runner、时间戳、原始轨迹、提交物、评分日志和结果。题目或评分规则变动后，记录修订原因、时间、实际影响，以及是否发生在观察模型结果之后；判断旧证据是否仍适用，受影响的可比 trial 用同一新版 Verifier 重判并保留新旧结果。检查是否为维持目标通过率而选择性新增检查、只重判部分可比 trial 或隐去改变结论的旧结果；新增检查、修复评分器缺陷和中性化修改分别说明。脱敏、重命名或字段删减后的文件标为派生副本，记录变化及语义复核。原始证据可按客户约定放在包外审计位置；不可用时说明，不能把派生记录称为未修改原件。
7. **复核报告。** 文件数、任务数、体积、运行结果和比率从本次送检包及原始记录生成。逐项核对报告结论可由明细复算，所有未读、未执行、异常、跳过及不适用项都有说明。

前置检查应服务于实际验证，不挤占必要的代码执行、模拟或测量。源码足以证明的缺陷可直接记录；仅仅没有在源码中发现缺陷，不构成运行或安全保证。

G-14 原编号对应第三方授权与再分发，本版不纳入；保留其余编号以便与原标准对照。报告无须给 G-14 状态，也不因缺少授权材料标 `BLOCKED`。

逐项状态使用 `PASS / FAIL / BLOCKED / N/A`：`FAIL` 表示已证实违反适用要求；`BLOCKED` 表示适用要求或关键内容尚无法确认；`N/A` 必须有不适用理由。若客户已有整包交付判定规则，按其规则报告。没有规则时，可报告“检查已完成/部分完成”及 G 项状态；只有所有适用 G 项通过且所有文件均有结论时，才可称“按本次检查范围全部通过”。此状态只描述交付检查，不替代 Task 的百分制质量分，也不新造质量及格线。

**本阶段的交付边界。** G-01/G-02/G-03/G-08 同时核对当前项目已确认的文件名、版本日期、品牌、语言、ZIP 与包外报告位置；若适用 Morrow Lab 特定命名或固定标题，按其现行书面约定逐字核对，不能将旧项目模板套到其他客户。英文交付如要求 ASCII 路径、只保留英文说明文件，应检查实际包内文件和路径；这是交付检查，不是 README 正文写作，也不要求本流程生成 README。当前只是过程包时，正式交付才会出现的文件或命名要求记录为“后续适用”，不把未到阶段的产物当作当前缺失。

## 5. Task 定义质量：Q1—Q8

八项均逐 Task 审阅，不删除顶层项或调整权重；无关子场景可注明不适用。目录、README、排版、专业文风或投稿格式仅在造成可定位的输入、配置、题意或评分缺陷时计入相应 Q 项，不单独计分。

| 项 | 权重 | 应核查的核心保证 |
|---|---:|---|
| Q1 题目定义清晰度 | 15 | 目标、输入、输出、单位、时点、边界、异常规则及优先级可确定 |
| Q2 题面与验收对齐 | 15 | 核心要求有验收；影响得分的检查有公开依据；口径、schema 与断言一致 |
| Q3 合法可解性与环境 | 15 | 输入、工具、预算和正式交接支持至少一种公开合法解 |
| Q4 规则与参考答案正确性 | 15 | 真值、科学或业务假设、数据和单位有独立依据 |
| Q5 验收对错误的识别能力 | 15 | 验真实产物；空执行、缺失产物和核心错误不能伪通过 |
| Q6 验收公平性 | 10 | 接受等价解，容差、顺序、表示与过程限制合理 |
| Q7 判分可靠性 | 5 | 随机、时钟、资源、非法值、跳过及异常不会误导结果 |
| Q8 防作弊与安全边界 | 10 | 私有答案、评分规则和 Reward 通道隔离；提交代码权限与执行链受控 |

细化时逐项核对：Q2 的评估目标和必要统计口径公开、schema/字段/类型一致，隐藏样本或数值容差本身不必公开；Q3 的必要输入、工具、预算及正式交接支持公开合法解；Q5 的分数聚合不掩盖核心失败，零执行、缺损产物、关键词或自报成功不能蒙混；Q6 的业务键、数值容差、顺序和实现限制不误拒合法替代；Q7 的随机性、时钟、测量开销、非法值、跳过与评分异常分别处理；Q8 追踪 Agent 和 Verifier 的实际身份、读写路径、提交代码执行链及宿主边界，不能仅凭分开目录或容器就认定隔离。参照任务既有 Reward 协议核对二元必需项与部分分项，不把本节百分制质量分反写成任务 Reward。

工作区与产物路径按任务自己的公开约定检查。`/workspace/input/`、`work/`、`evidence/`、`output/`、`answer.md` 只是可用的组织示例，不能无客户依据强制采用；真正需要确认的是模型能定位输入、在允许位置完成工作、通过正式交接提交可复核产物，并且评分器私有材料在解题阶段不可见。办公类结果需打开正式输出副本核查，代码调查类结果需把结论同源码路径、受控实验和原始输出对上。

每项从 100 分起，按已确认的**独立根因**扣分：轻微 10（局部不严谨，不改变核心答案）；中等 30（有明确局部反例，边界答案或局部得分可能错误）；严重 60（核心要求、常见合法解或关键结果受影响）；致命 100（核心保证失效，如无合法解、空执行满分、直接读答案或改分）。按实际后果和反例定级，不按文件数或修复工作量定级。分项最低 0 分。

同一根因在同一项只扣一次；跨项只在最直接的一项扣分，其他项注明“关联影响，已计入 Qx”。只有修复该根因后仍存在独立问题，才在另一项再次扣分。关联项虽未重复扣分，其保证若仍未满足，不得计为通过。每个缺陷记录位置、受影响行为、最小反例、证据、严重度理由、归属、整改建议及复验方法。

设第 i 项已确认扣分为 dᵢ，分项得分 sᵢ = max(0, 100 − dᵢ)，权重 wᵢ 如表。**质量分 = Σ(wᵢ × sᵢ ÷ 100)**；用未舍入值求和，最后保留 1 位小数。不加印象分、不设总分及格线。关键证据缺失时，该项记 `[0, max(0, 100 − 已确认扣分)]` 与待核查点；各项区间加权求和，报告“暂定质量分：下界–上界/100”。未知不等于 0 分，也不能只报上界或缩小分母。只有声明范围内八项都能确定时才给单一最终分。若只做静态审阅，明确写“静态审阅质量分”，不能冒充实测结论。

八项另给硬性标准状态：`通过`需全部适用保证有充分证据且满足；`未通过`存在已确认违反；`待核查`是尚无确认违反但关键证据不足。已确认缺陷同时伴随未知时，状态为未通过，并另列未知点。逐 Task 的 **Rubrics 成功率 = 已确认通过项 p / 8**，同时列未通过 f、待核查 u，满足 p + f + u = 8。它是未加权的状态比例，不能与质量分、模型 Reward 或机器测试通过率互换。没有开展审阅时写“0/8 已确认通过；8 项待核查”，不暗示八项均失败。确需包级值时，N 道独立题按通过分项总数/(8×N) 等权统计；包级质量分如需给出，也按独立 Task 等权平均并保留未知区间，突出单题严重问题。

难度、原创性和 AI 生成可能度可分别报告证据与局限，不计入质量分或硬性门槛。难度分析关注失败是否来自核心能力、合理边界或未充分公开的附带格式要求；起始材料若直接泄露全部解题位置或参考答案，应说明影响。不能仅凭成功率区间、文风或少量试跑作总体推断。

## 6. 运行、轨迹和比率口径

每次控制运行记录命令、工作目录、工具和 runner 版本、环境、身份、资源、退出状态、原始 Reward、实际测试执行/失败/跳过数、日志及产物。NOP 的失败必须是有效评分结果，不能由容器、权限或评分器异常冒充。复用镜像缓存时记录其范围；工作区、构建产物和可写卷是否沿用应单独说明，不把缓存命中写成干净构建证明。改动题目或 Verifier 后，受影响的运行保证须在新版重验；旧记录只作为历史证据。

已有 Trial 的状态至少区分正常完成、答案未通过、模型未完成、基础设施错误、资源终止、评分器错误和未知；Reward 为 0、Reward 缺失与评分未执行分开。发生 OOM 等资源终止时，区分提交前还是提交后，并据原始日志说明评分是否实际执行。重试、续跑或替换运行保留原 attempt、触发原因和纳入汇总的选择规则，不把多个 attempt 拼成一条轨迹。比较或合并结果前确认题版、Verifier、模型配置和运行条件足够可比。若已报告 token、缓存 token、成本等指标，还要注明原始来源字段、计算或聚合方法；本阶段无模型运行时不填虚构的消耗。

成功轨迹只引用满足该任务既有成功条件、且有可定位原始证据的单条 trial。部分得分且无既定成功阈值时称“代表执行”或“最高分执行”，不写“成功”。Reward=1 也要审阅 Verifier 覆盖范围外的实质正确性，发现残留核心错误时如实说明，不能包装为黄金正例。强弱模型对比必须基于同一任务版本、环境和 Verifier；不同会话的成功与失败不称作一次自主修复。

若已有轨迹被称为“自主修复”或用于训练价值分析，核对同一条 trial 中的**初始实质错误 → 触发检查 → 具体修复动作 → 最终重新验证**，再核查 Verifier 是否覆盖了该事实及是否仍有核心残留错误。不能仅因最终 Reward=1 倒推发生过自主修复。训练用途可据证据区分“可直接作为正例”“修复型训练候选”“不用于能力训练”；由环境、评分器、隐藏接口或不可解输入造成的失败不能当作模型能力难点。此分析只在已有可比轨迹且包或报告声称训练价值时适用，跑轨迹前不要求产生轨迹。

若观察模型结果后修改题面、参考数据或 Verifier，内部审计记录应保留修订时间、原因、影响范围及原/新结果。检查新增要求是否有独立任务依据、可比 trial 是否按同一新版规则重判，是否存在只挑有利槽位、隐去旧结果或以目标成功率倒推规则。无需因此新增 hash 或冻结流程；优先用现有版本记录、trial ID、原始日志和普通一致性测试追溯。

`Agent Step` 采用框架真实的主模型步骤口径，说明用户消息、工具观察、重试和子会话如何处理；JSONL 行数、工具调用数、轮数不能自动代替。`Agent wall time` 取同一 trial 的 Agent 阶段实际起止时间，说明模型等待和工具运行是否包含；不得使用总 job 耗时、预算上限或 Step 推算。每个 Step 和耗时都绑定任务、模型、配置、trial、状态和来源字段。**报告不计算跨轨迹 Step 合计、均值或范围。** 若原始平台另有“轨迹条目数”，以该名称逐 trial 展示，不称为 Agent Step。

Static 成功率列明对象、题版、规则、范围、分子、分母、异常和跳过处理。无既有定义时，以“确认成功项 p / 全部适用项 n”展示；适用但未执行、异常或待核查项留在 n 中并单列状态。分母无法确认时写“无法计算”。模型原始成功率仅按既有成功条件和可比 trial 计算，列出分子、分母、纳入/排除规则；小样观测不称为稳定能力成功率。机器验收条目通过率另列，不填入 Rubrics 成功率。

## 7. 本版质检报告的固定结构

报告是待检包外的 UTF-8 Markdown 文件，不生成 README。文件名以客户指定品牌、语言和命名为准；未指定时建议使用“`[Benchmark 名称]过程小样质量检查报告 [YYYY-MM-DD].md`”。若当前项目沿用 Morrow Lab 对 ZIP、报告及特定英文报告标题的书面命名约定，应核对实际品牌、Benchmark 名称、日期和标点；其他项目不继承该约定。正文事实和数字必须来自当前过程包及记录，不沿用旧批次，也不把尚未发生的轨迹写成失败。标题后直接进入 **“1. 总结”**，第一节只放**一张摘要表**；结论、严重问题与缺失证据写在表格行内，不再另加与之冲突的摘要段落。第二节固定为 **“2. 题面总结”**，先让读者理解任务，再进入检查过程。英文报告对应 `1. Summary`、`2. Task Summary`；若客户已有精确标题，按原样使用，例如 TB-science 的 `Morrow Lab：TB-science Sample Quality Inspection Report`。

### 7.1 第一节摘要表的最少字段

| 字段 | 填写规则 |
|---|---|
| 检查对象与范围 | Benchmark、任务数、目标数据集/子集、用途、交付包版本与路径 |
| 轨迹模型；上界模型；下界模型 | 正式模型 ID、已记录的配置及角色；未提供或未核实如实写明 |
| 轨迹步数；成功轨迹步数 | 按任务/模型/trial 逐条给值与口径；**不填跨 trial 合计** |
| 成功轨迹 | 任务、模型、trial ID、原始 Reward、Agent wall time、证据；无则写未获得 |
| 模型原始成功率 | 真实分子/分母、可比范围；无既定成功条件写无法计算 |
| Rubrics 成功率 | 每题 p/8 及 f/u；有必要时再给包级等权值 |
| Static 成功率 | p/n、规则、范围、未知与跳过；无法计算写原因 |
| Task 定义质量 | 每题质量分或暂定区间、主要扣分原因、静态/实测范围 |
| 交付检查与流程状态 | G 项 `PASS/FAIL/BLOCKED/N/A` 摘要；既有流程状态及依据，或无既有判定规则 |
| 关键问题与下一步 | 严重/致命缺陷、阻塞证据、优先整改 TODO；建议不得写成已完成 |

本阶段没有模型轨迹时，轨迹模型、成功轨迹、Step、wall time、模型原始成功率等摘要字段统一写“本阶段未运行，不适用”；不把 NOP 或 Oracle 当作模型成功轨迹，也不以 0/0、0% 或 `BLOCKED` 代替尚未到阶段的模型结果。控制运行、Static 和 Q1—Q8 的实际结果仍按证据填写。若已有 trial 或本次客户要求轨迹证据，再恢复下文完整 trial 口径。

### 7.2 后续章节

**2. 题面总结。** 每道题分别用短段或紧凑事实表说明领域与工作场景、目标数据集、任务目标、公开输入、预期交付、成功条件、必要约束及任务意图。从解题者可见材料独立复述；决定性歧义当场点出，并在 Q1 或对应项定位。不照搬私有答案，也不把审阅后发现的隐藏要求补写成原题要求。

**3. 检查范围、材料与指标口径。** 列客户要求、本次过程包和逐文件覆盖情况、文件类别、题版与环境、已执行/复用/未执行的检查、运行原始证据；已有 trial 时再列纳入规则、Step/耗时与比率定义。需要的总体任务指标表置于此节；成功 trial 表仅在已有有效轨迹时逐任务列行。总体情况后列待整改 TODO。报告的文件数、目录数、题数和体积可从清单复算。

**4. 逐 Task 详细质检。** 每题先列 Q1—Q8 八行：固定权重、独立缺陷与严重度、分项得分或区间、加权贡献、证据和整改验证方式；随后单列八项“通过/未通过/待核查”状态表，使 p+f+u=8。再列公开要求与 Verifier 双向对应、逐 criterion 的证据/失败边界、真值及最小反例、Oracle/NOP/Static 记录、正式交接和办公产物应用层复核。模型结果、成功轨迹、版本修订和训练价值只在已有对应证据时列出；未跑轨迹写明阶段原因。G 项问题可在相应任务处详述，并在总表索引。难度、原创性、AI 生成可能度如有评估，分别写证据与局限。

**5. 交付包 G 项明细。** 按 G-01—G-13、G-15 列状态、适用理由、具体路径、证据、未读文件、阻塞原因和复验方式；G-14 不纳入。逐文件覆盖清单可作为报告附录或同目录独立附件，报告须能定位它。任务质量、运行控制与轨迹证据分别给结论，不能被包面清洁或数字一致性替代。

**6. 整改建议与结果适用范围。** 依严重度和依赖关系列 TODO，写清责任对象、建议动作及验证方式；标识尚未完成。说明单次执行、静态审阅、未执行检查、未提供证据及不能外推的范围。严重/致命问题即使总分较高，也要在摘要和本节显著呈现。

正式报告不罗列无关试跑流水或全量失败表；统计必须保留必要分子、分母和范围，归因选择足以支撑结论的代表证据。异常和真实答案失败分别说明；日志仅证明失败现象时，不推断未被证实的算法根因。表格中的路径和证据链接须可定位，不能依赖作者口头说明。
